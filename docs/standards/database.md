# Database Standards

## Database Architecture Overview

This project uses PostgreSQL with:
- **Direct SQL queries** - No ORM abstraction layer
- **Denormalized counters** - Cached counts with timestamp tracking
- **Strategic UUID usage** - Only for external resources and sessions
- **Comprehensive indexing** - STORING clauses for covering indexes
- **Multi-tenant blocking** - User-level content filtering in queries

## SQL Style

- **Quotes**: Use double quotes for identifiers, single quotes for strings
- **Keywords**: Use UPPERCASE for SQL keywords (`SELECT`, `FROM`, `WHERE`)
- **Indentation**: Align clauses for readability
- **Parameters**: Use parameterized queries with `$1`, `$2` syntax

## Schema Patterns

- **Primary keys**: Use `{table}_id` pattern with `GENERATED BY DEFAULT AS IDENTITY`
- **Foreign keys**: Use `{table}_id` naming convention consistently
- **Timestamps**: Use `create_date TIMESTAMP(3) NOT NULL DEFAULT NOW()`
- **Booleans**: Use `BOOL DEFAULT false/true` with semantic names

## ID Conventions

**Critical distinction**: UUIDs are used ONLY for specific cases:

**UUIDs (CHAR(36))**:
- **S3 stored images**: `profile_picture_uuid`, `image_uuids` (comma-separated list)
- **Sessions**: `session_uuid` for stateless client identification
- **Reset tokens**: `token_uuid` for secure password reset links

**Auto-incrementing INTEGERs** (everything else):
- **Users**: `user_id`
- **Posts**: `post_id`  
- **Replies**: `reply_id`
- **Messages**: `message_id`
- **Conversations**: `conversation_id`
- **All other entities**

**Rationale**: UUIDs prevent enumeration attacks for S3 images and provide session security. Integers are more efficient for all internal references and relationships.

## Denormalized Counter Pattern

**Problem**: Counting favorites/replies in real-time is expensive at scale.

**Solution**: Cache counts with timestamp tracking:

```sql
-- Posts table includes denormalized counters
reply_count INT DEFAULT 0,
favorite_count INT DEFAULT 0,
counts_max_create_date TIMESTAMP(3) NOT NULL DEFAULT NOW()

-- Update pattern when favorites change
UPDATE posts
SET
  favorite_count = COALESCE(subquery.favorite_count, 0),
  counts_max_create_date = NOW()
FROM (
  SELECT COUNT(f.*) AS favorite_count
  FROM favorite_posts f
  LEFT JOIN flagged_posts l ON l.post_id = f.post_id
  WHERE f.post_id = $1
) AS subquery
WHERE posts.post_id = $1
```

**Client sync**: `getUpdatedCounts.js` fetches only counts that changed after client's last update using `counts_max_create_date > $1`.

## Complex Query Patterns

### Multi-tenant Content Filtering
Every content query excludes blocked users and flagged content:

```sql
SELECT p.*, u.display_name,
  CASE WHEN f.user_id IS NOT NULL THEN TRUE ELSE FALSE END as favorited
FROM posts p
LEFT JOIN users u ON u.user_id = p.user_id
LEFT JOIN favorite_posts f ON f.post_id = p.post_id AND f.user_id = $1
LEFT JOIN flagged_posts l ON l.post_id = p.post_id
LEFT JOIN blocked_users b ON b.user_id_blocked = p.user_id AND b.user_id_blocking = $1
WHERE
  l.post_id IS NULL        -- Not flagged
  AND b.user_id_blocked IS NULL  -- Not blocked
ORDER BY p.create_date DESC
```

### Session Validation with User Data
Single query for session validation and user info:

```sql
SELECT
  sessions.session_uuid,
  sessions.session_id,
  users.email,
  users.display_name,
  users.admin,
  users.user_id,
  users.profile_picture_uuid,
  users.slug,
  users.subscribed_to_users
FROM sessions
LEFT JOIN user_sessions ON sessions.session_id = user_sessions.session_id
LEFT JOIN users ON user_sessions.user_id = users.user_id
WHERE sessions.session_uuid = $1
```

### Dynamic Path-based Filtering
Topic and user filtering using conditional SQL (`getPagePosts.js`):

```sql
${req.body.path.startsWith("/topic/")
  ? `AND p.post_id IN (
      SELECT post_id FROM post_topics
      WHERE topic_id = (
        SELECT topic_id FROM topics WHERE topic_name = $4
      )
    )`
  : ""}
```

### Reply Ancestor Tracking
Denormalized ancestor relationships for thread queries:

```sql
-- reply_ancestors table tracks all ancestors, not just immediate parent
INSERT INTO reply_ancestors (reply_id, ancestor_reply_id)
SELECT $1, ancestor_reply_id 
FROM reply_ancestors 
WHERE reply_id = $2
```

## Indexing Strategy

### Covering Indexes with STORING
Minimize disk reads by storing frequently accessed columns:

```sql
CREATE INDEX idx_replies_parent_post_id_parent_reply_id_user_id 
ON replies (parent_post_id, parent_reply_id, user_id) 
STORING (body, note, create_date, favorite_count, counts_max_create_date)
```

### Multi-column Indexes for Common Queries
```sql
CREATE INDEX idx_notifications_user_id_create_date_read_seen 
ON notifications(user_id, create_date, read, seen)
```

## Data Types

- **IDs**: `INT GENERATED BY DEFAULT AS IDENTITY` or `CHAR(36)` for UUIDs
- **Timestamps**: `TIMESTAMP(3)` for millisecond precision
- **Text**: `VARCHAR(n)` with specific limits:
  - Post title: `VARCHAR(140)` 
  - Post/reply body: `VARCHAR(8000)`
  - Display name: `VARCHAR(50)`
  - Image UUIDs: `VARCHAR(147)` (4 UUIDs + 3 commas)
- **Booleans**: `BOOL DEFAULT false/true`

## Transaction Patterns

Most operations are single statements, but complex updates use implicit transactions:

```sql
-- Delete and recalculate in one transaction
DELETE FROM post_topics WHERE post_id = $1;
INSERT INTO post_topics (post_id, topic_id) VALUES ($1, $2);
```

## Performance Optimizations

- **Denormalized counters**: Avoid COUNT(*) queries at read time
- **Timestamp-based sync**: Only fetch changed data using `min_*_create_date` parameters
- **Covering indexes**: Include frequently read columns in STORING clause
- **LEFT JOIN for optional data**: Single query instead of multiple roundtrips
- **CASE expressions**: Compute booleans (favorited, voted) in SQL not application code
- **Path-based query splitting**: Different queries for posts vs messages vs notifications
